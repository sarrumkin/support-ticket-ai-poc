# AI Hub Support PoC — правила работы агента

## Назначение проекта

Экзаменационный System Design проект по направлению «Искусственный интеллект»: целевая AI/ML-система
для автоматизации обработки тикетов поддержки и минимальный воспроизводимый PoC. Не превращать
репозиторий в production-платформу и не добавлять код или инфраструктуру ради объёма.

## Slice workflow

1. Перед работой прочитать `docs/brief.md`, `SLICE_MAP.md` и документы активного слайса.
2. Несколько слайсов могут иметь статус `IN_PROGRESS`, только если их scopes независимы или между
   ними явно записана dependency. У каждого активного слайса должны быть отдельные issue и checkpoint.
3. Новый слайс определять только по фактической необходимости после явного checkpoint владельца и
   сразу добавлять в карту со статусом `IN_PROGRESS`.
4. Будущие слайсы и issues заранее не планировать и не создавать как placeholders.
5. При начале и завершении работы синхронизировать статус в `SLICE_MAP.md` и GitHub Project.
6. Не переходить к следующему слайсу без явного checkpoint владельца; старт параллельного слайса
   также требует отдельного checkpoint и фиксации зависимости от уже активных работ.

Допустимые статусы: `IN_PROGRESS`, `BLOCKED`, `DONE`. Канонический статус фактически созданных
слайсов хранится в `SLICE_MAP.md`; GitHub Project отражает тот же набор слайсов.

## Логирование решений и использования AI

После каждого содержательного решения дополнять `AI_USAGE.md`, не восстанавливать журнал задним
числом. Формат записи:

`проблема или вопрос → предложение AI → позиция Влада → общее решение → результат или проверка`.

Фиксировать не только согласие, но и отклонённые предложения, отложенные вопросы, ошибки AI,
обнаружившего ошибку и способ исправления. Не копировать полный чат и не выдавать предложение AI за
самостоятельное решение владельца.

В issue активного слайса хранить короткий `AI-CONTEXT` checkpoint: прогресс, решения, ключевые файлы,
блокеры и следующий шаг. Не дублировать в issue содержимое проектных документов.

## Инженерные правила

- Документация на русском; имена кода, API и устойчивые technical terms — на английском.
- Явно разделять реализованное в PoC, target design и assumptions.
- Синхронный hot path классификации/маршрутизации проектировать под ориентир `<= 500 ms`; генерацию
  ответа считать асинхронной.
- Risky, PII и low-confidence случаи не закрывать автоматически.
- Любое автоматическое решение должно оставлять audit record и объяснимую причину маршрута.
- Не добавлять внешнюю LLM, очередь, vector DB или production infrastructure без decision checkpoint.
- Для каждого слайса заранее фиксировать test decision и сохранять команды/результаты проверки.

## Privacy

Не коммитить секреты, реальные пользовательские или корпоративные данные, токены, приватные пути и
внутренние материалы работодателя. Fixtures должны быть синтетическими. Репозиторий считать
потенциально публичным, даже пока он имеет private visibility.
