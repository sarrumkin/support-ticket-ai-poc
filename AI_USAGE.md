# Использование AI

## Как ведётся журнал

AI используется как технический copilot для декомпозиции, критики решений, проектирования,
реализации, тестов и self-review. Влад остаётся владельцем scope и значимых решений. Ниже фиксируются
не стенограммы, а точки, где предложения сторон повлияли на результат.

| Этап / проблема | Предложение AI | Позиция Влада | Общее решение | Результат / проверка |
|---|---|---|---|---|
| Scope программы | Учесть полный перечень артефактов и отдельно решить судьбу product-документов | Требования AI Product к сдаче не относятся | Не создавать `product.md` и `WORKLOG.md`; обязательную минимальную бизнес-ценность оставить в README | Scope закреплён в `docs/brief.md` и `AGENTS.md` |
| Удалённый репозиторий | На основании исходной формулировки исследовать GitLab и предложить связку через issue Штаба | Уточнил, что имел в виду GitHub и его Project | Использовать private GitHub repo `sarrumkin/ai-hub-support-poc` и нативную repository-level связь с Project | Ошибочное направление остановлено до создания ресурсов |
| Видимость репозитория | Public упростит доступ проверяющему | Выбрал Private | Создать private repo; доступ проверяющего проверить перед сдачей | Публичные данные не раскрываются в bootstrap |
| Тайм-бокс | 12–20 часов позволили бы сделать более широкий PoC | Выбрал 6–8 часов | Исключить production infrastructure и удерживать минимальные tracer paths | Ограничение записано в scope и карте слайсов |
| Форма PoC | FastAPI + demo CLI в одном процессе | Поддержал вариант | HTTP-контракт и воспроизводимый CLI demo без отдельного worker | Реализация отложена до функциональных слайсов |
| ML/LLM baseline | Зафиксировать offline rules + TF-IDF + mock generation | Попросил не принимать решение заранее | Оставить baseline открытым decision gate Slice 2 | В `SLICE_MAP.md` вопрос отмечен как open |
| Структура skeleton | Создавать документы progressive, когда появляется проверяемое содержание | Выбрал full skeleton | Создать все обязательные AI-документы сейчас, но наполнить их статусом, критериями и открытыми вопросами вместо пустых TODO | Проверяется, что каждый файл содержателен |
| Project tracking | Один общий issue снизил бы overhead | Выбрал управление по слайсам | Создавать отдельный issue только при фактическом старте очередного слайса | Создан только [issue #1](https://github.com/sarrumkin/ai-hub-support-poc/issues/1); будущие слайсы имеют статус `PLANNED` только в карте |
| Ошибочная привязка Project | Интерпретировал «Project из штаба» как существующий Project `shtab` и привязал к нему репозиторий | Указал, что для проекта должен быть создан отдельный Project | Создать private Project private Project, перенести начатые слайсы и полностью убрать связь из `shtab` | Причина обнаружена Владом; repository link и items проверены через GitHub API, старые связи удалены |
| Переход к system design | Сначала проверить статус Slice 1 и не начинать реализацию tracer path до контракта | Явно решил перейти к Slice 2 и начать с точных продуктовых требований и pipeline | Перевести только Slice 2 в `IN_PROGRESS`, создать [issue #2](https://github.com/sarrumkin/ai-hub-support-poc/issues/2) и сначала согласовать продуктовый outcome | `SLICE_MAP.md`, README и GitHub Project синхронизированы; реализация Slice 3 не начата |
| Граница автоматизации | Предложил copilot-first или hybrid automation | Выбрал hybrid-вариант B и попросил перенести pipeline в Mermaid | Разрешить автоответ только для allowlisted, safe и high-confidence сценариев; остальные исходы — draft или human review | Outcomes и sync/async flow уточнены в `docs/ticket-processing-flow.md`; реальная внешняя отправка остаётся вне PoC |
| Ответ после routing policy | В первой Mermaid-схеме blocked/risky path показывал только последующий ответ оператора | Влад обнаружил, что policy не должна оставлять пользователя без немедленного ответа | Разделить sync status response и final support response; для любого принятого тикета вернуть статус «обрабатывается» или «передан оператору» | Обе ветки routing policy теперь возвращают status response в hot path; он явно не считается решением или основанием для автозакрытия |
| Граница human review | Поместил `human_review_required` и пользовательский status в sync subgraph, из-за чего decision смешивался с исполнением маршрута | Влад потребовал вынести всё выполнение human review из hot path | В hot path оставить только routing decision и status response; queue dispatch, ожидание оператора и ответ выполнять асинхронно | Mermaid-схема разделена на sync hot path, async human-review path и async answer path; конкретный persistence/queue contract остаётся открытым |
| Точность пользовательских статусов | Использовал общий status «принят в обработку или передан оператору» | Влад отметил, что пользователь должен точно понимать текущий путь, и предложил повторное уведомление при недоступной generation | Ввести явные статусы `processing_automatically`, `waiting_for_specialist`, `escalated_to_specialist`, `answered`; уведомлять о fallback только после фактической смены route, а не при каждом retry | Product status contract и повторный status event зафиксированы в `docs/ticket-processing-flow.md`; доставка должна быть идемпотентной и не раскрывать внутреннюю risk category |
| Происхождение auto-reply и второй gate | Ошибочно назвал auto-reply необязательным расширением и предложил убрать его из основной схемы | Влад напомнил, что исходный кейс допускает автоматический ответ для safe-категорий, а добавленной фичей является operator review сгенерированного draft | Оставить auto-reply core-возможностью; разделить `RoutingPolicy` до generation и `ResponsePolicy` перед отправкой, а при отказе второго gate передавать оператору draft и evidence | Исходный кейс сохранён в `docs/original-requirements.md`; схема исправлена; отсутствие подтверждённых thresholds/error rate записано production blocker в `docs/risks-and-ops.md` |
| KB-first для повторяющихся тикетов | Текущая схема направляла каждый safe-кандидат через retrieval и generation | Влад указал, что около 40% типовых обращений не требуют генерации и могут получать готовый текст из базы | Добавить `LayeredAnswerResolver`: exact approved answer → approved semantic search → generation fallback; 40% считать верхней оценкой candidate pool, а не auto-reply rate | Processing contract вынесен в `docs/ticket-processing-flow.md`; ML, risks, monitoring и README синхронизированы; LLM avoidance становится явной метрикой |
| Scope второй response policy | Распространил `ResponsePolicy` на exact, semantic и generated candidates, хотя approved content уже прошёл редакционную проверку | Влад отделил риск текста от риска сопоставления: exact lookup должен включать eligibility, а semantic lookup требует только match-confidence gate | Убрать отдельную policy с approved paths; оставить `GeneratedResponsePolicy` только для generated draft | Mermaid ведёт eligible exact и reliable semantic answers прямо в `auto_reply`; architecture и risks синхронизированы с новым boundary |
| Планирование слайсов | Изначально разложил весь проект на Slice 1–6 и хранил будущие работы как `PLANNED` | Влад решил создавать слайсы только по мере фактической необходимости и переименовать текущий scope по его реальному результату | Оставить в карте только созданные Slice 1 и Slice 2; назвать Slice 2 `Ticket processing flow`; будущий слайс добавлять сразу при старте после checkpoint | Удалены placeholders Slice 3–6; workflow, README и issue #2 синхронизированы; допустимые статусы сокращены до `IN_PROGRESS`, `BLOCKED`, `DONE` |
| Review processing flow | Обнаружил, что status delivery смешана с route decision, lookup miss не отделён от outage, а `answered` наступает до явного delivery confirmation | Влад решил не расширять завершавшийся Slice 2 и перенести замечания в отдельный архитектурный Slice 3 | Закрыть Slice 2 как reviewed processing contract; lifecycle, failure semantics и audit ordering сделать входными решениями Slice 3 | Review findings не выданы за дефекты уже реализованной системы и закреплены в границе нового слайса |
| Гарантия доставки событий | Предложил заменить фразу «идемпотентно не более одного раза», смешивающую idempotency и `at-most-once delivery`, на `at-least-once` processing с deduplication | Влад попросил сначала отдельно объяснить проблему, затем выбрал `at-least-once + dedup` | Записать проблему отдельным архитектурным решением; использовать стабильный `event_id`, delivery ledger и provider idempotency key при его поддержке | Решение входит в Slice 3 и должно быть проверено повторной доставкой одного события |
| Граница Slice 3 | Предложил target sizing с 2x headroom и локальным microbenchmark, не выдавая stub latency за production evidence | Влад выбрал отдельную lifecycle-диаграмму, design target 2x observed peak и deterministic PoC lifecycle без scheduler | Начать `Architecture, capacity and latency`; оставить production infrastructure, реальные модели и tracer paths вне scope | Slice 3 добавлен только после checkpoint владельца; будущие слайсы не создаются |
| Performance evidence | Предложил stdlib benchmark deterministic adapters с throughput и percentiles, но предупредил, что без реальных dependencies он измеряет только orchestration ceiling | Влад выбрал sizing + microbenchmark, а не только расчёты или полноценный load harness | Хранить benchmark рядом с явной evidence boundary и не использовать результат для replica sizing | 6 unit tests прошли; 20k synthetic tickets дали около 273k/s и p95 0.00325 ms на CPython 3.13/arm64, что записано только как локальный harness result |
| Проверка Mermaid | Первый запуск CLI через process substitution завершился без ошибки, но не оставил render artifacts; такой результат ошибочно выглядел успешной проверкой | Влад не вмешивался; несоответствие обнаружено AI при финальном evidence check | Не засчитывать exit code без файлов; повторить parsing через явные временные `.mmd` и проверить ненулевые SVG | Lifecycle, processing и architecture diagrams повторно отрендерены в SVG; временные файлы удалены |
| Project title Slice 2 | Попытался исправить устаревший Title карточки через `project item-edit`, но GitHub разрешает менять это поле только у draft items | Влад не вмешивался; рассинхронизация обнаружена AI на финальной проверке | Удалить только устаревший Project item, повторно добавить тот же issue #2 и вернуть status `Done` | Issue и история не затронуты; Project показывает актуальные названия трёх слайсов и не имеет `In Progress` items |
| Уровень абстракции processing diagram | Во время architecture review добавил в основной end-to-end flow persistence, outbox, delivery worker, confirmation и retry | Влад указал, что схема стала переусложнённой и implementation mechanics не относятся к product-level ticket flow | Вернуть исходную простую pipeline diagram; worker/outbox topology оставить только отдельной reference implementation diagram в architecture | Processing flow снова показывает routing/resolution/human outcomes, а architecture отдельно объясняет реализацию |
| Ошибочный status patch | При повторном открытии Slice 3 слишком широкий patch изменил первый `Status` в карте и временно пометил Slice 1 как `IN_PROGRESS` вместо Slice 3 | Влад не вмешивался; ошибка обнаружена AI до GitHub-синхронизации | Исправить статусы адресно по заголовкам слайсов и проверить единственный `IN_PROGRESS` локально и в Project | Slice 1 остался `DONE`, correction выполняется только в Slice 3; внешний неверный статус не публиковался |
| Граница ML-слайса | Предложил сравнить полноценные PoC и Prod stacks и подробно спроектировать PII boundary | Влад ограничил время и попросил сначала реализовать только минимальный PoC, а Prod-риски записать отдельно | Выбрать библиотечные baselines, synthetic RU fixtures и fail-closed поведение; production selection отложить | Slice 4 создан как `Minimal PoC ML baseline`; Prod assumptions и blockers должны попасть в `docs/risks-and-ops.md` |
| ML replaceability | Предложил единый provider-neutral contract для каждого ML-этапа | Влад потребовал обязательно записать все упрощения, альтернативы и архитектурно обеспечить замену каждой части | Orchestration зависит от `Protocol` interfaces и Pydantic DTO; concrete SDK/model metadata остаются внутри adapters и audit | Замена PII/classifier/retriever/generator не должна менять ticket flow или routing outcomes |
| Внешняя generation | Первоначально предложил OpenAI Responses API | Влад выбрал Groq с Qwen | Использовать официальный Groq SDK и `qwen/qwen3.6-27b` за `TextGenerator`; JSON валидировать локально и fail closed | Strict schema для Qwen не обещается; offline fixture generator остаётся обязательным для воспроизводимости |
| Exact lookup boundary | Первая реализация связывала approved answer только с intent | Влад требовал самые простые решения, но с безопасной заменяемой архитектурой | Оставить быстрый in-memory `dict`, однако ключом сделать точную нормализованную фразу из versioned KB, а не широкий intent | Smoke test подтверждает `auto_reply` без инициализации embeddings и без вызова generator |
| FastEmbed version behavior | Реальная semantic-проверка обнаружила предупреждение о смене pooling для multilingual MiniLM | Влад заранее потребовал честно фиксировать все упрощения и альтернативы | Не маскировать warning старым pin; считать threshold demo-level и требовать recalibration при обновлении model/runtime | In-memory Qdrant/FastEmbed path прошёл; ограничение и replacement trigger записаны в `docs/ml.md` и risks |
| Audit exact/semantic | Self-review обнаружил, что combined resolver указывал embedding model даже на exact path, где model не вызывалась | Влад требовал audit metadata каждого реально вызванного adapter/model | Сохранить один `AnswerResolver` contract, но возвращать разные `ComponentRef` для JSON dict и Qdrant/FastEmbed | Exact smoke test дополнительно проверяет отсутствие model metadata и lazy index initialization |
| Async transport PoC | Предложил сначала вернуть весь `status_events` в одном HTTP response, что не моделировало получение событий во времени | Влад указал, что HTTP нельзя держать до 15 минут, и выбрал максимально простой async PoC | `POST /tickets` возвращает `202`, полный Slice 4 processor идёт в `BackgroundTasks`, demo-клиент polling-ом читает in-memory state | Контракт вынесен в `docs/api-contract.md`; one-worker, restart loss и отсутствие real channel delivery записаны как ограничения, target остаётся queue/outbox + delivery worker |
| Представление test evidence | Сначала сообщил только счётчик passing tests и устно описал пути | Влад потребовал сохранить конкретные результаты и объяснить, что именно они доказывают | Записать команды, duration, smoke outcomes и evidence boundary в monitoring; external Groq считать непроверенным до запуска с локальным secret | `docs/monitoring.md` отделяет contract/integration evidence от ML quality, SLA и production claims; после безопасного добавления ключа полный suite дал `18 passed`, а synthetic Groq probe — reviewable grounded draft |
